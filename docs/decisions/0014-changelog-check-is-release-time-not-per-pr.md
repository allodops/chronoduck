# CHANGELOG.md content-equality is a release-time check, not a per-PR CI gate

## Context

Article II.2 originally read: "`CHANGELOG.md` ... begins with `<!-- generated by make changelog -->`
and equals `make changelog-check`. Enforced by `make hygiene`." Issue #24 called for
`scripts/changelog.mjs`, and PR #156 implemented that literally: `scripts/hygiene-selftest.mjs`
gained an assertion that `make changelog-check` was green against the real working tree, and CI's
required `hygiene` job runs `make hygiene-selftest` on every PR.

`CHANGELOG.md` is generated from `git log`, so what it should contain depends on `main`'s tip at
generation time. The moment any other PR merges to `main` while a given PR is still open, that
PR's own `CHANGELOG.md` — generated against an older tip — no longer matches what `make changelog`
would write today, through no fault of that PR's author and with no action they could have taken
in advance. Confirmed happening in practice on this exact PR (#156): its CI went red this way in
round 1, after unrelated PR #148 merged to `main` while it was in review, and #156 fixed the
problem in its own round 2.

## Decision

`make changelog-check`'s content-equality check runs at release time (`make release-checklist`
names it as a step) and remains available for anyone to run by hand at any time. It is no longer
part of `make hygiene-selftest`'s real-tree assertions, so it is no longer part of CI's required
`hygiene` job. The marker-prefix check (`CHANGELOG.md` must begin with the generated-by comment)
is unaffected — that's a property of the file itself, not of `main`'s current tip, and stays
enforced by `make hygiene` via `forbid-ledger.mjs` on every PR.

`scripts/changelog.mjs` and its synthetic-repo test in `hygiene-selftest.mjs` (a disposable 3-commit
git repo, not `main`) are unchanged and still prove both the red and green cases correctly — only
the assertion comparing against the *real* working tree was removed.

## Consequences

- A PR can carry a stale `CHANGELOG.md` without failing CI. This is intentional: staleness here is
  cosmetic (the file catches up the next time anyone regenerates it, typically the next PR's
  author) and only a release-time concern, not a merge-blocking one.
- `make release-checklist`'s step naming `make changelog` / `make changelog-check` is now the sole
  place content-equality is actually gated, by a human running the release process — not by CI on
  every PR.
- A future contributor reading Article II.2 should not expect `make hygiene` to catch a stale
  `CHANGELOG.md`; only its marker.
