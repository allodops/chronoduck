# Performance

Three kinds of number, kept in three places, compared under one rule. The methodology follows
cerberus's `benchmarks.md` with one change DuckDB makes possible: peak memory is measured, not
modelled.

## What is measured

Structural quantities first, because they are deterministic and portable across hardware: rows
scanned per query (the scan-bound contract, from `EXPLAIN ANALYZE`), peak state bytes per series
per state class, and for the aggregate form the intermediate row count. Statistics are chosen per
claim: best-of-N for single-thread micro costs, where the minimum is the cleanest estimate; median
± IQR and `p90/min` at eight threads for the parallel operator, where the tail *is* the property
"combinable" promises, and `p90/min > 1.5` is a scaling-lane failure in its own right. Then
throughput in the kernel's own units rather than wall time: *samples per second per core* for the
fold, *series × steps per second* for grid production, and their ratio — samples per output value,
the fan factor. Then the numbers users feel: wall time for a named query shape, and three memory
numbers for the same shape — tracked-allocator state bytes (the law), DuckDB's peak buffer memory
(the scan and the partition sort), and process peak RSS from `/proc` (the ceiling), one shape per
process. Finally the scaling curves — wall and RSS against thread count (1, 2, 4, 8, 16; the
speedup curve is the real claim behind "combinable"), against series count at fixed steps, against
steps at fixed series, and against the window/step ratio, which is exactly what the operator exists
to make irrelevant and what the aggregate form pays for.

## Three harness tiers

Micro-benchmarks with Google Benchmark, one per primitive: nanoseconds per sample for
`counter_fold`, per step for `window_walk`, per merge for `hist_add` at each scale pair. They run
on every PR and are ratcheted on structural counters only — allocations, comparisons — never on
nanoseconds. Kernel benchmarks through SQL over generated data, nightly, best-of-N wall and
measured RSS against a committed baseline; the gate is the structural side (rows scanned, the RSS
law) and wall time is informational with a benchstat-style confidence interval across runs. And a
published `benchmarks.md`, regenerated by one command with the host read from `/proc` and `/sys` at
generation time, where timings are presented as ratios and structural numbers verbatim.

## The dataset is a generator, not a file

Nobody's published numbers are comparable to ChronoDuck's unless data and query semantics match, so
every benchmark names a seeded, reproducible shape rather than a file. The generator follows the
TSBS-devops data model — hosts × metrics at a fixed cadence, the model every time-series vendor has
published against — extended with what TSBS lacks and this kernel cares about: counters with
resets, staleness gaps, native histograms at mixed scales, duplicate timestamps. The generator is
named `chronoduck-devops`, because with those additions it is a new benchmark and not a TSBS
variant, and the brief says so rather than borrowing TSBS's comparability. A benchmark line reads
"shape `devops-10k-15s-1h`, query `rate-sum-5m-15s`", and the query is stated as a fixture in the
kernel's own vocabulary, never as a query string, so the same line can be run against every oracle.
A seed does not pin a DuckDB file: load order (single-threaded, `preserve_insertion_order` on),
compression (`force_compression` for native storage; explicit `ROW_GROUP_SIZE` and `COMPRESSION`
for Parquet), storage format version and checkpoint threshold are all pinned, benchmarks run on the
default vector-size build only, and the generated file's checksum is recorded beside every
benchmark line — a line whose checksum differs from the baseline's is a new baseline, not a
regression.

**Shape sources, not comparables.** TSBS-devops query classes (`lastpoint`, `single-groupby-*`,
`double-groupby`, `high-cpu`) are not kernel folds as stated — `lastpoint` has no grid or lookback,
the group-bys are cross-series aggregates the kernel excludes — so TSBS is the generator's lineage
and nothing more. Mimir's published MQE figure (75 MB vs 954 MB on `sum by` over 100 k series) is a
whole-query number including chunk decode with no harness outside Mimir; it survives only as the
restated per-series-per-sample target above. Thanos's `BenchmarkRangeQuery` cases include binary
operators and subqueries over in-memory series with no scan; their shapes seed the generator, their
numbers do not appear.

The rule for every row: same generator, same fixture-stated semantics, same host and same day for
anything claimed as a ratio, and a "not comparable because" cell that is never empty for someone
else's number.

## Targets

So that the first benchmark run is a measurement and not a rationalisation, the design states
targets before the code that must meet them — stated so that only the kernel can satisfy them, not
the host. On the cerberus shape (`rate-sum-5m-15s`, 500 k samples) the operator's wall is within 2×
of chDB's native `timeSeriesRateToGrid` *measured the same day on the same host through the L6a
harness* — never a ratio to a number from another machine — and its tracked state bytes are below
chDB's reported per-query memory on that run. Resident state per series is stated per window sample
with the fixed overhead separate: `16 B × samples_in_window + c` for `RAW_WINDOW`, which is 320 B
at a 5 m window and 15 s cadence and 57 KB at 1 h and 1 s — a bare "under 1 KB per series" means
nothing without the shape. Speedup is measured on the extension operator's own timing from the
profiler, not on wall, because a serialising combine can hide behind a scan that parallelises on
its own; the target is 5× at eight threads on a ≥ 1 k-series grouped workload, and `p90/min ≤ 1.5`.
Rows scanned satisfy the two-gate rule above. A target the kernel misses is a design finding, not a
number quietly edited.
