# Architecture

> *Figure.* The kernel sits inside DuckDB's operator and aggregate contracts. Everything to the left is the host's; everything to the right is a consumer's.

## Where it plugs in

Four DuckDB entry points carry the surface, and the division between them is the design's main memory decision. A **custom sink-and-source operator** is the primary path for every range fold (`RAW_WINDOW` and `HIST_WINDOW`): no DuckDB extension operator inherits an ordering contract from its input, so the operator partitions rows by series hash, sorts each partition by `ts` in buffer-managed, spillable blocks, and then streams each partition through a two-pointer walk that holds one window plus the edge context. Its memory law is therefore *O(range) in a spillable sort plus O(threads × window) resident* — not "O(window)", which is the fold's law. That is still strictly better than the aggregate form, whose state heap cannot spill, and it is the shape of DuckDB's own window operator — which raises a concrete open question: build the sink, or express the range folds as windowed aggregates over grid-injected rows and let DuckDB's existing partition-sort do the work. Same law, far less operator code, C++-only either way; which of the two is chosen is an open question an ADR decides. The grid is bind data (constant `start, end, step`) today; a grid *relation* as a second child is a structurally different, not-yet-built alternative. **Aggregate functions** implement the instant (`LAST_K`), slice (`SLICE`) and histogram-merge (`HIST_MERGE`) folds, whose states are already small, with variable-size memory accounted through the tracked allocator — accounted, not spilled: DuckDB's external aggregation moves inline state rows to disk and does not follow a heap pointer, so no design here relies on spill. An aggregate form of the range folds is kept for small grids and for the storable `_state`/`_merge` pattern, with its O(range) memory documented and sentinel-tested rather than hidden, and with an `operator ≡ aggregate form` parity leg in the test plan for every range row. Output shape — one row per grid point, or one `LIST` per series — is an open question this document states rather than resolves: under a consumer `GROUP BY` the list form feeds a several-times smaller intermediate (which is why ClickHouse returns arrays), so both surfaces exist and the structural benchmark lane measures them before either is called canonical. **Table functions** provide `ts_grid` and the consumer front-ends' entry points. An **optimizer extension** pushes the scan bound `[start − window − lookback − anchor_extra, end + lookahead]` into the scan, scoped to `{Aggregate | ExtensionOperator} → [Filter] → Get` on native and Parquet scans; on a table-function source such as RawDuck, where partial pushdown drops unhandled predicates, the bound is asserted absent and the residual filter kept. The bound changes only rows read, never rows answered, which is why its test asserts on the plan's pushed predicate and on the rows-scanned counter.

## Why C++

The C extension API, and therefore Rust, covers scalar, aggregate and table functions and projection pushdown — but not filter pushdown into table functions, not window callbacks, not optimizer hooks, not custom operators (confirmed through March 2026). The aggregate family alone would fit Rust; the scan-bound pushdown, which is a memory-correctness property rather than an optimisation, does not. So the kernel is C++, following the `extension-template`, with the option of Rust numerics behind a C++ shell where a library earns it (the `anofox` pattern).

## State classes, edge modes, value domains

Every function declares one of five state classes. `RAW_WINDOW` holds `(t, v[, st])` samples and folds them in timestamp order — deterministic by construction; in the operator form one window per thread is resident and the partition sort spills, in the aggregate form the whole scan bound is resident. `SLICE` keeps one order-free partial per grid bucket — memory proportional to steps, deterministic for count, min, max, first and last, within the reorder bound for sums until reproducible summation (Demmel–Nguyen pre-rounding or a superaccumulator; compensated addition is not order-independent) retires that. `LAST_K(n)` keeps the n newest samples. `HIST_WINDOW` and `HIST_MERGE` are the histogram counterparts. Edge modes name what happens at the window boundary — `INSIDE`, `EXTRAPOLATE` (Prometheus classic: threshold 1.1×, half-interval fallback, zero clamp), `ANCHOR` (read the last sample before the window; VictoriaMetrics and Prometheus 3.13), `SMOOTH` (interpolate both edges), `LOOKBACK` (carry within lookback; a stale marker ends the carry). Value domains describe the input algebraically — `COUNTER`, `GAUGE`, `NONNEG`, `ANY`, `HISTOGRAM` — never by which language produced it; a span duration and a log-line count are just `NONNEG` and `ANY`.

## The three numeric contracts

Counters carry an optional **start timestamp** — OTel's `start_time_unix_nano`, the reference's per-sample `ST` — and it changes two things: a reset is `value drop ∨ st_reset`, where `st_reset` is the reference's four-case rule (unset; `ST ≥ T`; `ST < prevT`; `ST == prevT` with delta-versus-unknown disambiguation) — so a series whose start moved is a reset even with no value drop, which matters for delta temporality. And a single sample whose start timestamp lies inside the window yields a rate (`durationToStart = 0`, `sampledInterval = t − ST`, the first value counted), so "one sample → no value" is true only when no start-timestamp role is bound. Every `COUNTER`-domain function takes `start_ts` as an optional third input; the fixture literal is `[t, v, st]`; and MR-ST asserts that a value reset and a start-timestamp-only reset at the same point give the same `increase`.

Time is native `TIMESTAMP` (microseconds, a superset of the millisecond references), which is what makes `ASOF JOIN`, `generate_series` and interval frames work without casts. Staleness rides in the value: the reference's stale-marker NaN payload is preserved bit-for-bit in the `DOUBLE`, so `NULL` always means "no row" and the two NaNs are told apart by `is_stale`. Writers with no marker — OTLP carries a `NO_RECORDED_VALUE` flag, JSON cannot carry NaN at all — declare a boolean `stale` role in the profile instead, and `is_stale` reads either; a test round-trips the payload through Parquet, `CAST` and a sort, since nothing else proves DuckDB preserves it. Sums on the `D1` path use Neumaier-compensated addition with the compensation term carried in the partial state; the `D0` path for sums uses reproducible summation, because compensation bounds the error but does not make the result independent of order. Duplicate timestamps are resolved by a declared total order on the value's bit pattern (IEEE 754 `totalOrder`: `−0 < +0`, NaN payloads ordered), with the rule "keep the greatest under totalOrder, except that any NaN loses to any non-NaN and the stale marker loses to an ordinary NaN" — which is total, reproduces ClickHouse's documented behaviour, and is a ChronoDuck contract because the reference rejects differing duplicates at ingest and defines nothing. Histograms tie-break on `(count, compact-then-xxh3)` with the hash named and pinned by a fixture; `std::hash` is not acceptable. The operator deduplicates within a series run itself and never relies on the sort to do it.
