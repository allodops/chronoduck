# ChronoDuck Constitution

This document governs how ChronoDuck is built. It supersedes every other practice. It is amended
only by a pull request that also adds an ADR under `docs/decisions/` explaining the change.

**Version** 1.2.0 · **Ratified** 2026-09-04 · **Last amended** 2026-09-04

## Article I — What ChronoDuck is
ChronoDuck is a DuckDB extension providing time-series building blocks: grid-aligned range folds,
lookback resampling and mergeable histogram state, as SQL functions and one operator. `docs/design/`
holds the design, `docs/testing/` the testing discipline, `docs/decisions/` the reasons.

## Article II — The repository is not a ledger
1. Source, tests and docs describe what is — never what is in progress, planned or deferred.
   Work in progress lives in issues and pull requests; decisions live in ADRs. A numeric target a
   registered lane checks describes a contract, not progress.
2. No file matching the ledger denylist in `scripts/hygiene/forbid-ledger.mjs` may exist
   (initial set: `PLAN*`, `STATUS*`, `PROGRESS*`, `ROADMAP*`, `NOTES*`, `JOURNAL*`, `TODO*`,
   `docs/plan*`). `CHANGELOG.md` is the only generated narrative: it begins with
   `<!-- generated by make changelog -->` and equals `make changelog-check`. Enforced by
   `make hygiene`.
3. No TODO, FIXME, HACK, XXX or WIP comment without `#<issue>` on the same line, and that issue
   open. Enforced by `make hygiene` (requires `gh`; offline runs report this check as red).
4. Citations name constructs — `file.cpp:function:` followed by a backticked expression that
   occurs exactly once in `file.cpp` — never line numbers. A rename that breaks a citation fails
   `make hygiene`; that is the intended failure mode.

## Article III — One issue, one pull request
1. Every change lands through a PR that closes exactly one issue with `Closes #N`. PRs authored
   by `dependabot[bot]` are exempt from this article's body rules and still pass every check.
2. The issue fully describes the bug, feature or concern: goal, acceptance criteria, out of
   scope, parent, size. The PR describes only the execution: how, deviations, risk, evidence per
   criterion, discovered issues. `make pr-hygiene PR=<n>` rejects a PR whose body restates the
   issue: |shingles₈(PR body minus headers and the Closes line) ∩ shingles₈(issue body)| /
   |shingles₈(PR body)| > 0.15, or whose title equals the issue title (case- and
   whitespace-insensitive), or that lacks the required sections.
3. Out-of-scope work discovered during an issue becomes a new issue before the PR merges, with a
   parent and milestone where it has a home, linked from the PR under Discovered.
4. A PR touches only files the issue's scope implies (review, Article VIII.2).
5. PR titles are Conventional Commits and are linted; squash merges only.

## Article IV — Makefile and scripts
1. `Makefile` is the only project front-end: humans and CI run `make <target>`. It `include`s
   `extension-ci-tools/makefiles/duckdb_extension.Makefile` (mandatory — the distribution and
   code-quality reusable CI workflows invoke targets from it directly) and adds every project
   target beside that include; a project target never shadows one the include already defines.
2. Every script lives in `scripts/` as a Bun shell module (`.mjs`, `import { $ } from "bun"`).
   No bash files, no inline workflow logic, no other scripting language in the tree. Scans skip
   submodule paths.
3. The chain is `.github/workflows → make <target> → bun scripts/<name>.mjs`. A workflow step
   that is not `make …` (with `env:` allowed) after checkout and tool setup fails `make hygiene`,
   except a job whose entire content is `uses:` naming a reusable workflow or action whose ref
   `make check-pins` verifies.

## Article V — Registered means fenced
1. A function exists only through `src/kernel/registry.def`; the macro's expansion generates
   dispatch and the test-presence records every layer requires. A row missing from any roster
   fails the build, named after the row. This article is enforced from the PR that creates
   `registry.def`, which moves every earlier function into it.
2. `docs/testing/` is binding: layer map, rules, comparator derivation, determinism classes,
   memory laws, metamorphic relations, fixture families. Weakening one is an amendment.
3. No skip, soft assertion, tolerance file, allow-list or expected-failure set. The only
   sanctioned exclusion is a declared divergence in the comparator's closed enum; an enum value
   no fixture exercises is a failure.
4. Ratchets gate on identity, never counts: REGRESSED, VANISHED, ARRIVED-FAILING and UNRECORDED
   are all fatal.
5. A test not provably executed by an unconditional, failure-propagating lane does not count.

## Article VI — Language-unaware
1. No file parses or depends on a query language. The forbidden token set (initially the
   language names promql, traceql, logsql, logql, metricsql) and the exempt paths
   (`CONSTITUTION.md`, `docs/prior-art.md`, `docs/decisions/`, `docs/design/ecosystem.md`,
   `docs/design/coverage.md`, fixture provenance values) live in `scripts/hygiene/consumer-tokens.json`. Product names are allowed.
   Enforced by `make hygiene` on code and fixture keys.
2. Derivation tools and consumers live in other repositories.
3. Registry vocabulary describes folds, edges, grids and value domains.
4. One embedded mini-language is admitted: a grammar that is a standard's (ISO/IEC 9075-2:2016 §R row-pattern
   syntax), whose parser is a Tier primitive with its own fence, appearing only in fixture values. A consumer's
   grammar never is.

## Article VII — CI is checks, not agents
1. `main` is protected by a ruleset: linear history, squash only, zero required reviews, required
   status checks. No agent runs in CI. Implementation, review and merging are done by Claude Code
   on the owner's machine, one issue at a time.
2. The required set is small, fixed and fast (merge gate); heavier lanes run on push to `main`,
   release branches and nightly (release gate) and are not required; their red is a bug, never a
   tolerated state. A lane is registered in `.github/ci-lanes.json` or it is not a lane.
3. A required check is added only after its context has reported green on `main` at least once,
   only via `make ruleset-add-check`, run from the merged tree; a context absent from the lane
   registry is removed with `make ruleset-remove-check`.
4. Workflows declare least-privilege `permissions:`; actions are SHA-pinned; the
   extension-ci-tools workflow ref is the tag `make check-pins` verifies.

## Article VIII — The implementer
1. One issue at a time: claim (`in-progress`), branch `issue/<n>-<slug>` off `main`, implement
   the acceptance criteria, file discoveries, open one PR, address review on it, merge when
   green, label the next eligible tasks `ready`.
2. Review happens in a fresh session with only the PR and this document as context, using
   `.claude/rules/review.md`; it rejects out-of-scope files, restated issues, missing evidence,
   tolerances, unregistered functions and line-number citations. The review body starts with
   `Fresh-session review:`; `make pr-hygiene` requires one dated after the PR's last commit.
   Two rounds maximum; later findings become issues.

## Article IX — Amendment and precedence
1. Precedence: constitution → `docs/testing/` → `docs/design/` → ADRs → `AGENTS.md` → the issue.
2. A PR changing this file adds an ADR (status accepted), bumps the version, updates Last
   amended; `make hygiene` fails otherwise.
3. Every PR includes one line: `Constitution check: <articles touched>`.
